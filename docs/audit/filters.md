# Filters audit

Port: `packages/filters`. Upstream: the filter models that three tools each carry their own copy of:
`upstream/FilterTool/filters.js`, `upstream/AnalyticTune/AnalyticTune.js` and
`upstream/FilterReview/FilterReview.js`. FilterTool's and AnalyticTune's copies are the same maths
(AnalyticTune adds `Ang_P`, `feedforward`, `NotchFilterusingQ` and returns `H_total`); FilterReview's
is a different design (log-tracked notches, numerator and denominator accumulated separately, a
differently biased unwrap). Where the tools compute differently each variant is kept under its own
name, so every tool gets its own upstream's numbers.

Oracle: `src/test-utils/upstream.ts` loads one tool's script (with `Libraries/Array_Math.js`) into its
own `node:vm` context; the tests construct the upstream filter objects there and compare bit for bit
(`expectBitEqual`, NaN equal to NaN):

- `elements.test.ts`: `PID`, `Ang_P`, `feedforward`, `LPF_1P`, `DigitalBiquadFilter`,
  `NotchFilterusingQ` and `NotchFilter` through AnalyticTune's `evaluate_transfer_functions`
  (complex `H_total`) on four measured-rate grids, and `PID`, `DigitalBiquadFilter`, `NotchFilter`
  through FilterTool's (magnitude and phase).
- `harmonic-notch.test.ts` (added in this audit): 40 random `HarmonicNotchFilter` configurations,
  including every `_MODE` value (0 to 6 and a fractional one), `_OPTS` bits 0, 1 and 4, `_HMNCS` up
  to nine bits, `_ENABLE` of 1, 0, -1, NaN and 2, a zero `_FREQ` and `_REF`, negative throttle and
  fractional and NaN motor counts, with the operating point read through a stub `document` as
  upstream's `get_form` does; compared as AnalyticTune `H_total` and as FilterTool dB magnitude and
  unwrapped phase.
- `tracked-notch.test.ts`: FilterReview's `DigitalBiquadFilter` (cut-offs 20, 45.5, 0, -1, 400 and
  NaN, NaN added in this audit), `NotchFilter` (25 random cases through the reduced-depth and
  disabled branches) and `MultiNotch` with 2, 3 and 5 notches, comparing the accumulated numerator
  and denominator.
- `phase.test.ts`: `unwrap` (FilterTool and AnalyticTune) and `get_phase` (FilterReview) on random
  phases plus jumps landing exactly on the thresholds; `phase_scale` (added in this audit) on
  drifting unwrapped phases and on an aliased max/min pair.

Statuses: **identical** (same result, restructured or typed code), **code-improved**,
**presentation**, **convenience**, **browser-forced**, **reverted-in-this-audit**.

## Resolved in this audit

- **`phase_scale` aliasing.** Upstream wraps the arrays in place. When the selected time range holds a
  single FFT window, FilterReview's `Phase_max` and `Phase_min` are the same array (both assigned
  `HR_phase`), so with "wrap" selected that array is shifted once for each of the two slots: 720°
  wherever the mean is shifted by 360°. The port copied each input, which wrapped max and min once
  and so drew a different envelope. `wrapPhase` now maps repeated input references to one shared
  copy, which reproduces the double shift without mutating its inputs; Filter Review's
  `bodeResponse` returns the same array for max and min in that case, as upstream. Oracle test:
  `phase.test.ts` "shifts an array passed twice twice".

## Proven upstream bugs fixed

Fixed only because each is proven to the standard in [`../bug-proofs/README.md`](../bug-proofs/README.md);
the verdicts are in [`../bug-proofs/filters.md`](../bug-proofs/filters.md).

- **Chained harmonic-notch copies differ** (`FilterTool/filters.js:287-290`,
  `AnalyticTune/AnalyticTune.js:497-500`). With multi-source ESC tracking and a double or triple notch,
  upstream computes each motor's spread inside the copy loop after the first copy has clamped the
  centre, so motors at the same frequency get different notches (ArduPilot uses one spread for every
  centre, `HarmonicNotchFilter.cpp:383-386`). `designHarmonicNotch` computes the spread once per
  harmonic, before the copy loop, so every copy equals the first: the reproduction gives
  `[18.2, 23.4, 18.2, 23.4]` instead of `[18.2, 23.4, 19.55, 22.05]`. The oracle tests compare with
  upstream patched the same way (`patchChainedSpread`) and check that the original differs only in
  this case. Tests: `harmonic-notch.test.ts` "proven upstream bug fixed: chained copies of a clamped
  harmonic equal the first copy", "differs from the original only in the proven chained-spread case";
  proof `proofs/filters/filters.test.ts`.
- **Single-window phase band shifted twice** (FilterReview `redraw_post_estimate_and_bode` + `phase_scale`). Fixed in
  Filter Review, not here: `bodeResponse` now returns distinct max and min arrays for a single window, so the band is
  wrapped once (see [`filter-review.md`](filter-review.md)). `wrapPhase` still shifts an array passed twice twice, as
  upstream's `phase_scale` does (`phase.test.ts` "shifts an array passed twice twice").
