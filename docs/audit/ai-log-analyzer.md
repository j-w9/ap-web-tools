# Audit: AI Log Analyzer

Port: `apps/ai-log-analyzer`. Upstream: `upstream/AILogAnalyzer/` (`index.html`, `logAnalyzer.js`,
`instructions.txt`, `assistantTools.json`, `styles.css`), plus `modules/JsDataflashParser/parser.js`.

Standard: [`docs/porting-policy.md`](../porting-policy.md). No test reaches OpenAI.

## Oracle tests

- `src/chat/upstream-flow.test.ts` runs upstream `logAnalyzer.js` in `node:vm`
  (`src/test-utils/upstream-analyzer.ts`: a minimal fake DOM, a fake of the v4 SDK calls it makes,
  the upstream parser) and the port (`connectAssistant`, `runTurn`, `updateAssistant` on the real
  v7 SDK adapter `openAiAssistantsApi` over a fake `fetch`) against identical fake OpenAI servers
  (`src/test-utils/fake-openai.ts`). For each scenario the HTTP request log (method, path, query,
  JSON or multipart body), the chat lines (notices, user and assistant text), the number of key
  prompts, the API keys clients were created with and the Update Assistant label must be equal.
  Scenarios: create the assistant and stream a reply; reuse the assistant and answer `get` from a log
  (old `output.json` files deleted, upload, cancel, fixed message, new run, chart download, next
  message attaches the file); no-log, no-data and unsupported calls (the attachment is then left out);
  a mixed batch followed by a second round of calls; a 401 while connecting, then a new key; a 401
  at send time while opening the thread; a failed message post, a failed run and a stream `error`
  event; a chart that cannot be downloaded; Update Assistant, and a failed delete.
- `src/analysis/message-data.test.ts` compares the `get` tool's JSON byte for byte with upstream's
  `window.get` on the upstream parser, for every message type of two real logs and a synthetic log,
  plus odd keys (`constructor`, `__proto__`, `toString`, `undefined`, `null`, `''`, …).
- `src/assistant/openai-backend.test.ts` checks `isUnauthorizedError` against upstream's function
  (cut out of `logAnalyzer.js`) on 18 values, and the backend's request sequences and error texts on
  a fake API.

## Upstream bugs reproduced

Each is also listed in [`../upstream-bugs.md`](../upstream-bugs.md).

1. `window.get` keeps only the last instance of an instanced message (`for … output = log.get_instance(…)`),
   so `get("IMU")` returns the highest IMU instance only.
2. Numeric columns are typed arrays, so the uploaded JSON has `{"0": v0, "1": v1, …}` objects instead of arrays.
3. A no-data failure sets the remembered `fileId` to `undefined`, so later messages are posted without
   `attachments` and lose the previous file.
4. In a mixed batch, successful calls are submitted without `output`.
5. The run is cancelled and a message is posted without waiting for the cancellation; the API may reject the
   message while the run is still cancelling.
6. Every `output.json` on the account is deleted, whatever its purpose or origin, without waiting; a second
   call in the same batch can list (and delete again) files whose deletion is still running.
7. Only a 401 while connecting asks for a new key; a key revoked later keeps failing with "Sorry, …".

## Proven upstream bugs fixed

Proven to the standard in [`../bug-proofs/README.md`](../bug-proofs/README.md); verdicts, reproductions
and fix details are in [`../bug-proofs/ai-log-analyzer.md`](../bug-proofs/ai-log-analyzer.md).

- **#137** `.log` files were offered ("Click to upload .bin/.log files for analysis") but only `.bin`
  was read, and "Log File Ready" was shown anyway. The port reads exactly the files upstream read; any
  other chosen file gets the error notice "<name> was not read: only .bin logs can be analysed." and
  is not reported ready; the earlier log, if any, stays in use (`analysis/log-file.ts`, `App.tsx`
  log handler; test `analysis/log-file.test.ts`).
- **#140** Errors in the tool handler and in the connection started from the key form were unhandled
  rejections with nothing shown. No port change was needed: the port already catches them and shows
  their text (`chat/session.ts` `connectAssistant`, `chat/turn.ts` `runTurn` with
  `assistant/openai-backend.ts` `toolFlowFailure`; tests `upstream-flow.test.ts` "a 401 at send time
  while creating the thread shows both upstream lines", `turn.test.ts` "turns thrown errors into
  notices instead of rejecting", `openai-backend.test.ts` "names failures in the tool flow, and stream
  errors with upstream text"). These are now recorded as a proven fix rather than a crash-clause
  difference.

## UI audit

Captured with `node scripts/ui-audit.mjs ai-log-analyzer` (states in `scripts/ui-audit-misc.mjs`) at
1440, 1024 and 390 px in both themes: empty, log loaded, a rejected key, a reply scrolled into view, and
a full conversation. The OpenAI REST API is answered in the page by `page.route` with recorded-shape
JSON and SSE (assistant list, thread, message, runs with `requires_action`, file list and upload,
cancel, chart download from `test-fixtures/ui-chart.png`, a failed run). No real key is used and
nothing reaches OpenAI. Presentation changes only; no request, text sent to OpenAI or tool output
changed, and every test passes with its expected values untouched.

Findings and fixes:

- Code blocks in replies showed the page's inline `code` box on every line: `pre code` is reset.
- Markdown tables squeezed their cells on phones (numbers broke across lines): tables scroll inside the
  bubble, cells do not wrap, and headings are styled.
- The transcript had no edge, so a reply scrolled under its top looked cut off: it is now a framed
  scroll box. On phones assistant bubbles use the full width and padding is tighter.
- Why the message box is disabled was only in a disabled, low-contrast placeholder: it is shown as text
  under the box (and linked with `aria-describedby`). The box has the accessible name "Message".
- Focus rings on the message box and the chart buttons use `--focus-ring` (readable in light mode).
- "Log File Ready" in the Visualizations summary is now sentence case ("Log file ready").

Kept on purpose: "Update Assistant" / "Updating..." / "Update Failed" and upstream's chat texts
(including the lower-case tool failure texts) are upstream strings pinned by the oracle; the audit above
decided they stay identical.

Remaining: the rejected-key capture logs Chrome's own "Failed to load resource: 401" console line for
the mocked response; that is the browser reporting the intended error, not a page error.
