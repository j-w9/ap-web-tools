# Audit: AI Log Analyzer

Port: `apps/ai-log-analyzer`. Upstream: `upstream/AILogAnalyzer/` (`index.html`, `logAnalyzer.js`,
`instructions.txt`, `assistantTools.json`, `styles.css`), plus `modules/JsDataflashParser/parser.js`.

Standard: [`docs/porting-policy.md`](../porting-policy.md). The data the assistant receives is compared
byte for byte with upstream's `window.get` run on the upstream parser
(`src/analysis/message-data.test.ts`). The OpenAI flow is tested against a fake API
(`src/assistant/openai-backend.test.ts`); no test reaches OpenAI.

Status values: **identical** (same result, possibly restructured code), **presentation**,
**convenience** (added or changed UX that changes no computed result), **browser-forced**,
**crash** (upstream throws; the port shows an error instead).

## Upstream bugs reproduced

1. `window.get` keeps only the last instance of an instanced message (`for … output = log.get_instance(…)`),
   so `get("IMU")` returns the highest IMU instance only.
2. Numeric columns are typed arrays, so the uploaded JSON has `{"0": v0, "1": v1, …}` objects instead of arrays.
3. A no-data failure clears the remembered `fileId` (`fileId = await get(…)` returns `undefined`), so later
   messages lose the previous attachment.
4. In a mixed batch, successful calls are submitted without `output`.
5. The run is cancelled and a message is posted without waiting for the cancellation; the API may reject the
   message while the run is still cancelling.
6. `.log` files are offered in the picker but never parsed, yet "Log File Ready" is shown.
7. Every `output.json` on the account is deleted, whatever its purpose or origin.
