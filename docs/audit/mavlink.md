# Audit: MAVLink (`@apwt/mavlink`)

Upstream: `upstream/modules/MAVLink/mavlink.js` (pymavlink's `mavgen --lang=JavaScript_NextGen`
output with `runtime-fixes.patch` applied, see its `README.md`) and the jspack it loads
(`modules/MAVLink/local_modules/jspack/jspack.js`). Port: `packages/mavlink/` (`src/` runtime,
`scripts/` generator, `definitions/` XML). Users: Simple GCS, Telemetry Dashboard. Stream Stats
keeps its own tables from `StreamStats/mavlink_msgs.js`; the package's `tables.ts` offers the same
kind of lookup from upstream `mavlink.js`'s definitions.

Standard: [`docs/porting-policy.md`](../porting-policy.md). Status values: **identical** (same
result, restructured code), **API shape** (same information, typed TypeScript form),
**convenience**, **crash** (upstream throws; the port throws `RangeError` instead).

## Provenance of the definitions

Upstream's header says "Generated from: all.xml,ardupilotmega.xml,ASLUAV.xml,...". Running pymavlink's
generator on `all.xml` of ArduPilot/mavlink commit `5e496e27fa8108b669cb435d4472823cd7b7a711`
(2025-07-26, the head of ArduPilot/mavlink pull request #413, one commit on top of `master` at
`6cd16c5c`) reproduces upstream's file from `// enums` to the end of `mavlink20.map` byte for
byte, comments included; reverting `runtime-fixes.patch` makes the whole file identical apart from
the header note and whitespace. No commit on `master` matches (the nearest lacks
`MAV_DO_REPOSITION_FLAGS_RELATIVE_YAW`, `_VTOL_HOVER` and `_FW_LOITER`). Those 17 files are vendored
in `packages/mavlink/definitions/` (see its `README.md`); the package was previously generated from
`ardupilotmega.xml` at a newer commit (`0d734a4`, 2026-10-01), which lacked the ASLUAV,
development, test, ualberta, storm32 and AVSSUAS messages and had renamed or renumbered enum
entries.

## Tests

Oracle tests run upstream `mavlink.js` unmodified in `node:vm` (`src/test-utils/upstream.ts`):

- `src/oracle.test.ts`, definitions: the same 347 message ids, names and CRC_EXTRA; every message's
  fields in XML order and wire layout (the jspack format string derived from the descriptors equals
  `mavlink20.map[id].format`); the same 205 enums with every entry and value (2101 entries, mavgen's
  `NAME_ENUM_END = last + 1` included).
- `src/oracle.test.ts`, payloads: 8 random payloads of every message (any bytes, including text with
  NULs and bytes above 127) decoded by both and compared field by field, then re-encoded by upstream
  `pack` and by the package to the same frame bytes. jspack value packing: integer clamping and
  truncation, NaN, -0, float32 ties, long strings, characters above U+00FF, byte arrays, missing
  float elements and omitted extensions, the omitted-array cursor shift with its checksum holes, and
  the cases where upstream's `pack` throws.
- `src/parser.oracle.test.ts`, framing: the same chunks fed to `MAVLink20Processor.parseBuffer` and to
  `MavlinkParser.parse` must give the same messages (header, signed flag, link id, frame bytes) and
  the same discarded byte runs (upstream's `BAD_DATA`), in order, with equal
  `total_bytes_received` / `total_packets_received` / `total_receive_errors`, signing counters,
  `stream_timestamps` and signing timestamp. Named cases: every split of two coalesced frames,
  byte-by-byte input, noise, bad CRC, a false start marker, a corrupted length byte, unknown ids,
  truncated frames, MAVLink 1/2 mixing (short and long MAVLink 1 payloads), incompatibility flags,
  and signing (good, replayed, stale new stream, wrong key, unsigned, with and without an
  allow-unsigned callback, no key). A fuzz test of 40 random streams (valid, signed, replayed,
  corrupted, truncated, unknown-id, bad-flag frames and noise, three signing modes, three chunkings)
  asserts every path was taken.
- `src/parser.oracle.test.ts`, signing: signed frames byte for byte against upstream `pack` for link
  ids 0/7/255, timestamps 0 to past 2^48 and a 16-byte key; SHA-256 and `create_signature` against
  `mavlink20.sha256` / `create_signature` for 13 lengths and short/long keys; the initial timestamp.
- `src/fixtures.test.ts`: port of upstream `tests/mavlink.test.cjs` on `tests/fixtures/mavlink.json`.
- `src/generated.test.ts`: the checked-in `src/generated/` equals the generator's output.

## Remaining intentional differences

All are API shape: the same bytes, values and decisions, in a typed form.

- Messages are `{ name, id, fields, header, signature, frame }` with camelCase field keys, so field
  names cannot collide with metadata (upstream's `crc` collision cannot happen). Tools that expose
  upstream's object shape (Telemetry Dashboard widgets) rebuild it from these.
- 64-bit values are `bigint`; arrays are typed arrays; `char[n]` is a string without its trailing
  NUL padding. Upstream's representations (`[low, high, unsigned]`, strings for byte arrays) carry
  the same numbers.
- Enum objects per enum, without mavgen's `*_ENUM_END` markers.
- Discards are typed events (`garbage` with `noise` / `crc` / `incompat-flags`, `unknown`,
  `rejected` with the signature reason) instead of `BAD_DATA` messages with text reasons.
- Signing is a `MavlinkSigning` object passed to the encoder (sign outgoing) and parser (verify);
  an empty key, which upstream treats as "off", is refused: omit signing instead. The callback
  receives the frame header (with the message id) instead of `(processor, msgId)`.
- HEARTBEAT's `mavlinkVersion` is a field the caller fills (3), not a constructor default.
- The parser can be given a subset of messages (smaller bundles); the encoder can also write
  MAVLink 1 frames.
- No EventEmitter, logger or transport: `parse` / `push` return what they found, `encode` returns
  the bytes.
